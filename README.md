# 仕様・設計ドキュメントと Copilot 指示のテンプレート

## 目的

このリポジトリには、アプリ開発で再利用できる仕様・設計ドキュメントと Copilot リポジトリ指示のテンプレートを保存する。

| ファイル | 用途 |
| --- | --- |
| `specs/spec.md` | プロダクトの目的、対象範囲、機能・非機能要件、受入条件を定義する |
| `specs/plan.md` | アーキテクチャ、コンポーネント、API、セキュリティ、運用方針を定義する |
| `specs/tasks.md` | フェーズ、タスク、依存関係、完了条件を管理する |
| `specs/tests.md` | テスト方針、環境、ケース、受入条件との対応を定義する |
| `specs/data-model.md` | エンティティ、属性、関係、整合性、保持方針を定義する |
| `.github/copilot-instructions.md` | Copilot が常時参照する正本文書、実装方針、検証コマンドを定義する |

## 使用方法

1. 5つのテンプレートを対象プロジェクトの `specs` ディレクトリへコピーする。
2. `.github/copilot-instructions.md` を対象プロジェクトの同じパスへコピーする。
3. `{{PLACEHOLDER}}` をプロジェクト固有の値へ置換する。
4. `<!-- ... -->` の補足コメントを確認し、不要になったコメントを削除する。
5. 対象外の節を削除し、必要な節を追加する。
6. 文書間の用語、要件 ID、テスト ID、リンクを揃える。
7. 人間によるレビュー後、文書情報のステータスと更新日を変更する。

テンプレート自体へ特定プロジェクトの情報を書き込まない。再利用可能な構成上の改善だけをテンプレートへ反映する。

## プレースホルダー規約

プレースホルダーは `{{UPPER_SNAKE_CASE}}` 形式で記述する。

| プレースホルダー | 内容 |
| --- | --- |
| `{{PROJECT_NAME}}` | プロジェクトまたはプロダクト名 |
| `{{DATE}}` | `YYYY-MM-DD` 形式の更新日 |
| `{{STATUS}}` | `初版・レビュー待ち`、`承認済み` などの状態 |
| `{{PRODUCT_SUMMARY}}` | プロダクトの要約 |
| `{{PRIMARY_USER}}` | 主な利用者 |
| `{{CLIENT_TECH}}` | フロントエンドやクライアントの技術 |
| `{{BACKEND_TECH}}` | バックエンドの技術 |
| `{{DATA_STORE}}` | データストア |
| `{{AUTH_PROVIDER}}` | 認証基盤 |
| `{{DEPLOYMENT_TARGET}}` | 実行・デプロイ先 |
| `{{EXTERNAL_SYSTEM}}` | 主な外部システム |
| `{{OBSERVABILITY_PLATFORM}}` | ログ、メトリクス、トレース基盤 |
| `{{REPOSITORY_SPECIFIC_RULES}}` | コードや設定から推測できない、リポジトリ固有の安定したルール |
| `{{LINT_COMMAND}}` | Lint を実行するコマンド |
| `{{TYPE_CHECK_COMMAND}}` | 型チェックを実行するコマンド |
| `{{TEST_COMMAND}}` | テストを実行するコマンド |
| `{{BUILD_COMMAND}}` | ビルドを実行するコマンド |

必要に応じてプレースホルダーを追加する。同じ意味の値には文書間で同じ名前を使用する。

## 記述ルール

- 文書は日本語で記述する。
- 要件には `FR-*`、非機能要件には `NFR-*`、受入条件には `AC-*` の一意な ID を付ける。
- テストケースには `UT-*`、`IT-*`、`E2E-*` など、テストレベルが分かる ID を付ける。
- 未決事項は推測で埋めず、「確認事項」として担当者と期限を記録する。
- 実装詳細を仕様書へ過剰に入れず、技術上の判断は技術設計書または ADR に記録する。
- 受入条件とテストケースの対応を維持する。
- 秘密情報、実在利用者の個人情報、アクセストークンを記載しない。

## 利用前チェック

- [ ] `{{` または `}}` を含む未置換のプレースホルダーがない
- [ ] 対象外の節と補足コメントを削除した
- [ ] 文書間のリンクが有効である
- [ ] 用語と状態名が文書間で一致している
- [ ] 主要な機能要件に受入条件がある
- [ ] 受入条件に対応するテストケースがある
- [ ] 未決事項に担当者と確認期限がある
- [ ] 人間によるレビューを実施した
